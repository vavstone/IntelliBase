# Ограничения IntelliBase

Честный список: где система отказывается отвечать, где ошибается и что
осталось за рамками. Разделы 1–2 — про качество и границы применимости,
3 — осознанные компромиссы, 4 — техдолг перед промышленной эксплуатацией.

## 1. Где система отказывается отвечать или ошибается

**Порог релевантности отсекает не только мусор.** Если лучший найденный
фрагмент ниже `RAG_SCORE_THRESHOLD` (0.78), система отдаёт отказ, не вызывая
LLM. Порог откалиброван под конкретную embedding-модель
(`intfloat/multilingual-e5-large`): на демо-корпусе релевантные вопросы дают
0.795–0.911, нерелевантные — 0.695–0.766, порог стоит в зазоре. У E5
косинусное сходство сжато — зазор узкий. **При смене embedding-модели порог
нужно калибровать заново**, иначе часть валидных вопросов будет получать
отказ (или наоборот — система начнёт отвечать по нерелевантным фрагментам).
Вопрос из «серой зоны» 0.766–0.795 может быть отнесён в любую сторону.

**Context precision — самая слабая метрика RAG.** 0.705 против 0.952 у
faithfulness: retrieval приносит в контекст лишние фрагменты. Ответ при этом
не hallucinated (faithfulness высокий), но часть источников в выдаче
избыточна. Разбор и план улучшений — `docs/rag_evaluation.md`, разделы 7–9.

**Четыре вопроса из 27 в датасете оценки получили faithfulness ниже 1.0.**
Разбор каждой строки — `docs/rag_evaluation.md`, раздел 9.

**Вопрос без предмета получает неустойчивый ответ.** Фраза «укладываемся ли в
норматив по времени?» не называет ни процесса, ни нормы — а нормативов в корпусе
несколько (загрузка суточного пакета — 45 минут, время закрытия обращений —
1,8 дня, и другие). Предмет система достраивает по контексту диалога, и ответ
меняется от прогона к прогону. Замерено 06.10 в трёх условиях: в чистом чате —
ответ про норматив «не более 4 часов»; после разговора про поддержку — «норматив
для среднего времени закрытия обращений в источниках не указан»; в живом диалоге
— «обращения закрыты в течение 1,8 рабочего дня». Тот же вопрос **с предметом**
(«…загрузка суточного пакета… укладываемся ли мы в норматив по времени?»)
отвечает верно и со ссылкой на протокол испытаний. Практический вывод: вопрос
должен называть предмет. Короткие follow-up'ы («а для них?») разрешает condense,
но он опирается на историю диалога, а не на намерение пользователя: если тема
сменилась, переписанный запрос может увести поиск в предыдущую тему.

**Ответы синтезируются только по найденному контексту.** Модель не обращается
к внешним источникам и не знает того, чего нет в корпусе. Это осознанное
решение (оно же защищает от галлюцинаций), но означает, что вопрос по теме
документа, если нужный фрагмент не найден retrieval'ом, получит отказ.

## 2. Границы применимости

**Сканы не индексируются.** Страницы PDF без текстового слоя (`needs_ocr`)
пропускаются и в индекс не попадают — в логе это видно как
`pdf_type=scanned`. OCR не подключён: встроенный OCR pdf-inspector для
русского не годится (в словаре PP-OCRv6 нет кириллицы), а полноценный
русскоязычный OCR — отдельная задача с ощутимыми требованиями к ресурсам.
Документы, которые целиком являются сканами, для системы не существуют.

**Корпус — русскоязычный.** Embedding-модель многоязычная, но датасеты
оценки и корпус — на русском; качество на других языках не измерялось.

**Структура корпуса задаётся папками.** Категория документа = папка верхнего
уровня (`RAG_DATA_DIR`), файл в корне попадает в «Разное». Плоская загрузка
без раскладки по папкам ухудшает фильтрацию по подсистемам.

**Демонстрационный корпус синтетический.** `data/demo_kb` — 18
сгенерированных документов, а не реальная документация. Они согласованы между
собой и покрывают 7 подсистем, но не отражают хаос настоящего архива
(разнородное форматирование, вложенные таблицы, устаревшие версии рядом с
актуальными). Рабочий корпус (70 документов) в git не хранится.

**Часть категорий пуста.** В рабочем корпусе заведены подсистемы, документов
по которым нет (`postkontrol`, `tamozhnya_pravo`, `pravoohrana`, `crsved` —
0 файлов, см. `docs/data_inventory.md`).

**Отправка документов ограничена Telegram.** Получатель должен быть в списке
доступа к боту и хотя бы раз начать с ним диалог — Telegram не даёт боту
написать первым. Файлы: только pdf/docx/txt/md/xlsx/csv, до 50 МБ (лимит
Telegram).

**Агент ограничен числом шагов** (`MAX_ITERATIONS = 6`): сложная задача,
требующая большего числа вызовов инструментов, будет остановлена.

## 3. Осознанные компромиссы

**Проверка доступа сосредоточена в боте.** Бэкенд доверяет заголовку
`X-Owner-External-Id`, который проставляет бот. Гейт (`bot_users`, миграция
`d4e7a1b93c25`) стоит в middleware бота и закрывает все обработчики. **При
выставленном наружу порту 8000 проверку можно обойти прямым HTTP-вызовом** —
перенос проверки на сторону API запланирован как работа перед промышленной
эксплуатацией.

**Подтверждение отправки — само-подтверждение, а не «четыре глаза».** Кнопки
показываются тому, кто попросил. Это защита от **ошибки системы**: человек
видит адресата и файл до отправки и может отменить неверное. Это не защита от
**злоупотребления**: пользователь с доступом к боту может попросить рассылку и
сам же её одобрить. Круг получателей при этом ограничен серверным списком
`bot_users`, а не тем, кого назвала модель. Полноценные «четыре глаза»
(подтверждение в чате администратора) — следующий шаг, не реализован.

**Модерация: второй слой выключен по умолчанию и работает fail-open.**
Реализовано два слоя: локальный regex-блоклист и облачный OpenAI Moderation API.
Облачный **выключен по умолчанию** (`MODERATION_USE_OPENAI=false`) — сознательно:
он требует выхода в интернет (VPN или прокси), рабочего ключа OpenAI и
**отправляет текст пользователя во внешний сервис**, что для внутренней базы
знаний вопрос политики, а не техники. Второй слой включается флагом, когда он
действительно нужен. При недоступности API запрос пропускается (fail-open):
блокировать весь чат из-за сбоя внешнего сервиса сочли худшим исходом. При этом
срабатывания любого слоя пишутся в таблицу алертов.

**Резервная модель медленная.** При недоступности облачного провайдера запрос
уходит на локальную Ollama (ADR-003): на CPU это 15–20 с на ответ вместо ~2 с.
Резерв сохраняет работоспособность, но не заменяет облако по скорости —
деградация заметна пользователю.

**Разрыв стрима посреди ответа не переигрывается.** Резерв подхватывает
создание потока (до первого токена). Если провайдер отвалился, когда часть
ответа уже ушла пользователю, повтор не делается — иначе текст пришёл бы
дважды.

**Кэш работает только для детерминированных ответов.** Кэшируются запросы с
`temperature=0`; при ненулевой температуре ответы не кэшируются.

**Реранкер выключен по умолчанию** (`RAG_RERANK_ENABLED=false`): модель
`bge-reranker-v2-m3` весит ~2.2 ГБ. Включается вручную при наличии ресурсов;
влияние на метрики измерено в `docs/rag_evaluation.md`.

## 4. Техдолг перед промышленной эксплуатацией

| Проблема | Последствие | Что нужно |
|---|---|---|
| Токены по умолчанию (`change-me-admin`, `change-me-internal`) | предсказуемые секреты | заменить на `openssl rand -hex 32` перед публикацией |
| Проверка доступа на стороне API не реализована | обход гейта при открытом порту 8000 | проверять доступ в API, а не только в боте |
| «Четыре глаза» на отправку | нет защиты от злоупотребления правом | подтверждение в чате администратора |
| Два чат-роутера: `/chat` (legacy) и `/chats` | дублирование кода и API | консолидация |
| `/chat` без резервного провайдера | legacy-путь не отказоустойчив | перевести на общий `llm_fallback` (ADR-003) |
| Схема сервисов в `ARCHITECTURE.md` и `docs/diagrams/` устарела | расхождение документации и кода | перерисовать с учётом DeepSeek, агента и Phoenix |
| Уведомление администраторов о запросе доступа не реализовано | пользователь передаёт свой id вручную | уведомление в чат админа |

Полный список технического долга с датами — `docs/tech_debt/`.

## 5. Планы развития

Текущая версия — прототип: один клиент (Telegram), ручная раскладка корпуса по
папкам, плоская таксономия «документ → одна категория». Дальше — продуктовое
развитие: целевая архитектура и roadmap по фазам проработаны отдельно
(внутренние документы, в репозиторий не входят).

**Таксономия.** Сейчас категория — одно ПС, документ лежит ровно в одной
категории, а документ о нескольких подсистемах уходит в «Разное» и не находится
при фильтре по конкретной ПС (см. `docs/tech_debt/category-taxonomy-ps-*`).
Планируется: канонические ключи тегов в JSONB вместо одиночной категории,
извлечение тегов моделью с подтверждением человеком, фильтрация RAG по
нескольким тегам.

**Загрузка пакетами.** Сейчас документы кладутся в `data/kb/<категория>/`
и индексируются через `scripts/ingest.py`. Планируется приём ZIP-архивов
произвольной вложенности: очередь фоновых задач, статусы обработки,
дедупликация по хешу файла и текста, версионность документов.

**Другие клиенты.** Реализован Telegram-бот. Целевые интерфейсы —
корпоративный мессенджер (Yandex Messenger) и браузерный интерфейс: загрузка
документов, статусы обработки, браузер корпуса, разметка тегов,
администрирование ролей. Бэкенд к этому подготовлен: клиент отделён от API,
пользователь идентифицируется по внешнему идентификатору, список доступа
ведётся на сервере — новый клиент подключается к тем же эндпоинтам.
